## 1. 核心问题

### 1.1 结局过度集中

5000 局中 Top 5 结局占比 75.2%：

| 结局 | 占比 |
| --- | ---: |
| 英语领读生 | 24.4% |
| 中考定位成功 | 19.9% |
| 二模阴影 | 13.9% |
| 手机上交奇效 | 8.7% |
| 双一流稳妥录取 | 8.3% |

80 个结局中，5000 局只命中 50 个，30 个完全未出现。未出现结局集中在顶尖录取、志愿隐藏线、失败线和部分 B 档路线。

### 1.2 B/D 档存在感不足

单档分布：

```txt
B: 3.2%
D: 1.9%
```

虽然合并后的 A/B、C/D 目标达标，但玩家体验上会感觉普通稳定局多，明确的低报、滑档、重大失误和保底路线少。

### 1.3 录取院校过度集中

录取 Top 2：

| 院校 | 占比 |
| --- | ---: |
| 桂林电子科技大学 | 46.0% |
| 四川农业大学 | 23.6% |

两所合计 69.6%。主因是当前默认 profile 只有 31 条投档线，496 到 569 分段、580 到 615 分段和 620 分以上高分段都缺少足够候选。

### 1.4 滑档率过低

当前滑档率只有 0.1%。低 `VOL`、高 `RSK`、志愿风险事件对最终录取的影响还不够明显。

### 1.5 成长属性触顶

平均属性：

```txt
INT/STR/MNY/SPR: 10.0 / 9.9 / 4.0 / 4.5
```

`INT` 和 `STR` 基本触顶，后半程成长差异被压平，事件奖励的辨识度下降。

## 3. 任务拆分

### 任务 A：模拟器指标增强

状态：已完成

写入范围：

- `tools/simulate.mjs`
- `docs/balance-report.md`

目标：

- 让模拟器直接输出本计划需要的诊断指标，避免每次人工抄结果。

实现要求：

- 输出结局覆盖数：`observed endings / total endings`。
- 输出未命中结局清单，按 tier 分组。
- 输出 Top 1 / Top 3 / Top 5 结局集中度。
- 输出录取 Top 1 / Top 2 / Top 5 院校集中度。
- 输出分数段分布：`<420`、`420-499`、`500-549`、`550-579`、`580-609`、`610-639`、`640+`。
- 输出属性触顶率：`INT=cap`、`STR=cap`、`SPR=cap`、`VOL=cap`。
- 输出低志愿高风险样本数：`HVOL<25 && RSK>=65`。

验收：

```bash
node gaokao-restart/tools/simulate.mjs 5000
```

输出中必须包含 `Ending coverage`、`Ending concentration`、`Admission concentration`、`Score buckets`、`Cap rate`。

### 任务 B：录取投档线扩充

状态：已完成

写入范围：

- `src/content/zh-cn/admissions/universities.json`
- `src/content/zh-cn/admissions/admission-lines.json`
- `docs/admission-data-sources.md`

目标：

- 解决院校集中度问题，让同一分数段有更多真实可选学校。

数据原则：

- 继续使用当前默认口径：广西 2024 首选物理 本科普通批。
- 每条线必须有 `sourceName`、`sourceUrl`、`sourcePublishedAt`。
- 不虚构投档线。
- 同一学校可以有多个专业组，但 UI 必须能显示专业组。

优先补充区间：

| 分数段 | 目的 | 建议数量 |
| --- | --- | ---: |
| 420-499 | 普通本科、民办本科、地方本科兜底 | 15-25 条 |
| 500-549 | 普通一本、区域强校、低分捡漏 | 20-30 条 |
| 550-579 | 低线 211、双一流、强区域院校 | 20-30 条 |
| 580-609 | 中档 211、普通 985 冷门组 | 20-30 条 |
| 610-639 | 985 主体池 | 15-25 条 |
| 640+ | 顶尖 985 和强势专业组 | 10-20 条 |

第一轮已将录取线从 31 条扩充到 307 条，超过至少 80 条的要求。

验收：

- `validate-content` 通过。
- 5000 局录取 Top 1 院校占比 <= 25%。
- 5000 局录取 Top 2 院校占比 <= 45%。
- 985/211 实录率不脱离目标范围。

### 任务 C：录取算法调平

状态：已完成

写入范围：

- `src/engine/admission.ts`
- `tools/simulate.mjs`
- `tests/admission.test.ts`

目标：

- 让 `VOL/HVOL`、`RSK` 和志愿事件对实际录取产生更明显影响。
- 增加低志愿高风险局的降档和滑档概率。

建议改动：

- 将当前“按分数利用率排序取第一名”的选择改成带权随机，权重仍偏向更合适的院校，但避免所有局都选同一所。
- 增加 `strategyScore < 10` 且 `RSK>=65` 时的滑档概率，而不是只在极窄条件下直接滑档。
- 对触发 `志愿翻车`、`专业误读`、`提交惊险`、`名校滤镜` 类事件的局增加降档权重。
- 对触发 `志愿稳健`、`章程避坑`、`三角比较` 类事件的局降低滑档权重，提高压线录取权重。
- 新增 `highScoreLowAdmission` 统计：分数可达 211/985，但实际低一档或更多。

验收：

- 滑档率进入 1.5%-4%。
- 高分低报、盲冲滑档类结局在 5000 局中稳定出现。
- 低志愿高风险局的实际录取层级明显低于高志愿低风险局。

### 任务 D：结局条件与优先级重平衡

状态：已完成

写入范围：

- `tools/generate-expanded-content.mjs`
- `src/content/zh-cn/endings.json`
- `tests/engine.test.ts`

目标：

- 降低高频早期事件结局覆盖。
- 提高 B/D 档和志愿录取线结局出现率。

建议改动：

- 降低以下高频结局优先级或增加附加条件：
  - `英语领读生`
  - `中考定位成功`
  - `二模阴影`
  - `手机上交奇效`
- 给 B 档增加更宽的普通录取路线，例如：
  - 分数 500-560 且 `VOL>=35` 的“保底院校守住”。
  - 分数 520-580 且 `MARGIN>=30` 的“普通本科好专业”。
  - 分数 540-590 且 `VOL<30` 的“高分低报遗憾”。
- 给 D 档增加更明确的失败路线，例如：
  - `RSK>=70 && VOL<25`。
  - 触发志愿风险事件且最终录取层级低于可达层级。
  - `SPR<3 && RSK>=75` 的大考冻结。
- 将部分录取结局逐步迁移到录取结果条件，等待任务 E 支持新 token 后执行：
  - `ADM?[985]`
  - `ADM?[211]`
  - `ADMSCORE>=650`
  - `MARGIN>=20`

验收：

- Top 1 结局 <= 16%。
- Top 3 结局 <= 45%。
- 5000 局结局覆盖 >= 62/80。
- B 档 6%-10%，D 档 4%-8%。
- SSS/SS、S/X、A/B、C/D 大分组仍达标。

### 任务 E：结局条件支持录取 token

状态：已完成

写入范围：

- `src/engine/condition.ts` 或当前条件解析所在文件
- `src/engine/life.ts`
- `src/app/types.ts`
- `tests/engine.test.ts`
- `tests/admission.test.ts`

目标：

- 让叙事结局能引用真实录取结果，而不是只引用 `HSCR`。

新增条件建议：

```txt
ADM?[985]
ADM?[211]
ADM?[doubleFirstClass]
ADM![985]
SCHOOL?[10593]
ADMSCORE>=650
MARGIN>=20
SLIDE=1
```

实现顺序：

1. 先在 `FinalResult` 或结算上下文中暴露 admission 字段。
2. 条件解析器支持只在最终结算时读取 admission。
3. 保留旧条件兼容，不一次性重写全部 80 个结局。
4. 先迁移 8-12 个录取强相关结局。

验收：

- 单测覆盖 `ADM?[985]`、`ADM?[211]`、`ADMSCORE>=650`、`MARGIN>=20`。
- 旧结局条件仍能通过。
- 5000 局无异常。

### 任务 F：属性成长与上限复核

状态：已完成

写入范围：

- `src/engine/life.ts`
- `tools/simulate.mjs`
- `tools/generate-expanded-content.mjs`
- `docs/balance-report.md`

目标：

- 降低 `INT/STR` 后期普遍触顶造成的同质化。

备选方案：

方案 1：上限从 10 调整到 12。

- 优点：保留成长反馈，减少触顶。
- 风险：分数公式必须同步降权，否则平均分会升高。
- 配套：把 `INT`、`STR` 分数权重下调约 10%-15%。

方案 2：保留上限 10，减少事件成长收益。

- 优点：改动小。
- 风险：玩家仍容易感觉后期奖励浪费。
- 配套：削减高频事件的 `INT/STR` 正收益，更多改成 `VOL/RSK/SPR/SCOREMOD`。

建议第一轮选择方案 2。只有在内容扩充后仍大量触顶，再进入方案 1。

验收：

- 5000 局 `INT=cap`、`STR=cap` 触顶率下降。
- 平均最终分数仍在 565-590 区间。
- 985/211 实录率不明显失控。

## 4. 推荐实施顺序

第一轮只做可控优化：

1. 任务 A：模拟器指标增强。
2. 任务 B：录取投档线扩充到至少 80 条。
3. 任务 C：录取算法从确定性选择改为带权选择，并提高滑档/降档存在感。

第二轮再碰结局：

4. 任务 D：压低 Top 高频结局，补强 B/D 路线。
5. 任务 E：支持录取 token，迁移部分录取强相关结局。

第三轮处理成长：

6. 任务 F：根据新模拟结果决定是否调整属性成长。

## 5. 验收流程

每轮改动后必须执行：

```bash
node gaokao-restart/tools/validate-content.mjs
node ..\node_modules\vitest\vitest.mjs run
node gaokao-restart/tools/simulate.mjs 5000
node ..\node_modules\vite\bin\vite.js build
```

报告更新：

- 更新 `docs/balance-report.md`。
- 更新 `docs/08-task-status.md` 的当前平衡状态。
- 如果扩充录取数据，更新 `docs/admission-data-sources.md`。

## 6. 不建议本轮做的事

- 不要为了分布好看伪造投档线。
- 不要一次性重写全部 80 个结局条件。
- 不要同时大改分数公式、事件效果、录取算法和结局优先级。
- 不要把滑档率调到过高。标准版目标是“有风险感”，不是“志愿恐怖游戏”。
